# MILESTONES — בדיחה בלחיצה

**מסמכי מקור:** `PRD.md`, `ARCHITECTURE.md`, `DESIGN.md` (והתמונות `wireframes.png`, `style-guide.png`, `mockups.png`).

## עקרונות מנחים

- הפיתוח מיועד למסך מובייל אחד בלבד, בעברית וב-RTL, ללא תפריט או מסכים נוספים.
- מימוש לפי ה-Technology Stack שנבחר: React, TypeScript, Vite, CSS, Vercel Function, OpenAI Responses API במודל `gpt-5` (דרך `OPENAI_MODEL`), ו-`vite-plugin-pwa`.
- אין Database, Authentication, שמירת היסטוריה או Rate Limiting של המוצר.
- כל Milestone מסתיים בתוצר שניתן להריץ ולבדוק. רכיבי תשתית המוקמים לפני חיבור ה-AI לא יוצגו למשתמש כיכולת שכבר עובדת.
- ה-PRD גובר על רכיבים דקורטיביים סותרים בתמונות; בפרט אין לממש את אייקון התפריט שמופיע בחלק מה-Mockups.
- לכל Milestone יש סעיף **"דרישות מוקדמות מבעל המוצר"**. אם אחת מהן לא בוצעה כשמתחילים לבנות — עוצרים ומבקשים אותה, צעד אחר צעד ובשפה פשוטה.
- האפליקציה מחוברת ל-Vercel כבר מ-Milestone 1. כל דחיפה מאושרת ל-`main` מעדכנת את הכתובת הציבורית, ובה נבדקות הדרישות שתלויות בטלפון אמיתי.

## Milestone 1 — הקמת פרויקט, מסך ראשי ופריסה ראשונה ✅

**שם ומטרה:** לבסס אפליקציית מובייל ניתנת להרצה עם המסך היחיד ועיצובו, ולפרסם אותה בכתובת HTTPS — לפני חיבור לשירות ה-AI.

**דרישות מוקדמות מבעל המוצר:**
- קובץ `spec/assets/kitten.png` (ראה DESIGN 2.4.1).
- חשבון Vercel (חינמי) וחיבורו לחשבון GitHub — בהדרכה צעד אחר צעד, בשלב הפריסה.

**מה יש לממש:**
- יצירת פרויקט React + TypeScript עם Vite, תשתית CSS, וסידור Repository יחיד עבור Frontend ו-Backend בהמשך.
- מימוש מסך **"בדיחה בלחיצה"** בהתאם למבנה ה-Wireframes ולעיצוב ה-Style Guide וה-Mockups: כותרת, שדה נושא עם מונה תווים, לחצן **"צור בדיחה"**, שורת סטטוס וכרטיס בדיחה במצב ריק — עם הטקסטים המדויקים מ-DESIGN 1.3.
- ממשק RTL בעברית, צבעי המותג (כולל Raspberry לכפתור), גופני Heebo/Assistant המאוחסנים באפליקציה, רכיבים מעוגלים, פריסת עמודה אחת ותמונת החתלתול.
- שדה נושא אופציונלי המוגבל ל-100 תווים, עם מונה `0/100`.
- הגדרת תצוגת טקסט אזור הבדיחה כך שתתמוך גם בתוכן LTR ותוכן ארוך, ללא גלילה אופקית.
- עד לחיבור השירות **הכפתור מושבת**; אין להציג בדיחות שמתחזות לתוצאה של GPT-5.
- חיבור ה-Repository לפרויקט Vercel (Framework Preset: Vite) ופריסה ראשונה מ-`main`. הפריסה דורשת push — לפי CLAUDE.md, עוצרים ומבקשים אישור לפני ה-push.

**תוצר מצופה:** מסך מעוצב ותקין, הנפתח גם מקומית וגם בכתובת `*.vercel.app` בטלפון; ניתן להזין ולערוך נושא, אך טרם ניתן להפיק בדיחה.

**Definition of Done:**
- הפרויקט מותקן, נבנה ללא שגיאות TypeScript ונטען מקומית.
- כל הרכיבים מופיעים במסך יחיד, בפריסה הדומה למקורות העיצוב, עם הטקסטים מ-DESIGN 1.3 וללא תפריט ניווט.
- הממשק בעברית ו-RTL; הזנת 100 תווים מתאפשרת, תו 101 אינו מתקבל, והמונה מתעדכן.
- תצוגת המובייל אינה גורמת לגלילה אופקית; במחשב מוצגת עמודה ממורכזת.
- הכתובת הציבורית ב-Vercel נפתחת ב-Chrome בטלפון ומציגה את אותו מסך.
- אין מפתחות API או סודות בקוד הלקוח או ב-Repository.

## Milestone 2 — יצירת בדיחה מקצה לקצה ✅

**שם ומטרה:** לספק את ה-Vertical Slice המרכזי: הזנת נושא, יצירת בדיחה חדשה ב-GPT-5 והצגתה באותו מסך.

**דרישות מוקדמות מבעל המוצר:**
- חשבון OpenAI עם אמצעי תשלום ויתרה.
- **תקרת הוצאה חודשית קשיחה והתראת תקציב** מוגדרות בחשבון OpenAI (לפני שמחברים מפתח).
- מפתח API שהוזן לקובץ `.env` המקומי (Claude יוצר `.env.example` ו-`.env` עם שמות המשתנים בלבד).
- אותו מפתח (או מפתח נפרד) הוזן כ-Environment Variable בפרויקט ב-Vercel, לפני הדחיפה של Milestone זה.

**מה יש לממש:**
- Vercel Function ב-TypeScript עבור `POST /api/joke`, כולל אימות קלט בצד השרת, טיפול בנושאים ריקים/רווחים והחזרת JSON לפי חוזה ה-API שב-ARCHITECTURE (כולל `422 TOPIC_NOT_ALLOWED`).
- שימוש ב-OpenAI SDK וב-Responses API עם המודל מ-`OPENAI_MODEL` (ברירת מחדל `gpt-5`), `reasoning effort` מינימלי ו-`verbosity` נמוך; יצירת בדיחה בנושא שהוזן ובשפתו, או בדיחה כללית בעברית כשהנושא ריק; כללי התוכן מה-PRD בתוך ההוראות.
- Timeout של 20 שניות מול OpenAI ו-`maxDuration` של 30 שניות ל-Function.
- הרצה מקומית ב-`vercel dev` (לאחר `vercel link`) עם המפתח מ-`.env`.
- חיבור הכפתור ל-`/api/joke` באמצעות בקשה חדשה בכל לחיצה, והחלפת הטקסט בכרטיס הבדיחה ללא שמירת היסטוריה. השבתת הכפתור בזמן בקשה (מימוש בסיסי; מצבי הטעינה והשגיאה המלאים ב-Milestone 3).
- תצוגת בדיחה כ-Plain Text בכיווניות המתאימה לשפת התוצאה.

**תוצר מצופה:** משתמש יכול להזין נושא או להשאיר את השדה ריק, ללחוץ על הכפתור ולקבל בדיחה אמיתית שנוצרה ב-GPT-5 — גם מקומית וגם בכתובת הציבורית.

**Definition of Done:**
- בדיחה בנושא בעברית מוצגת בעברית; בדיחה בנושא באנגלית מוצגת באנגלית; שדה ריק או רווחים בלבד מפיקים בקשה לבדיחה כללית בעברית.
- נושא שאינו מאפשר בדיחה לכל הגילאים מחזיר `422` ולא בדיחה.
- שתי לחיצות עוקבות לאחר השלמת הבקשה מפעילות שתי בקשות יצירה נפרדות, והבדיחה החדשה מחליפה את הקודמת בכרטיס הקיים (ללא הבטחה ששתי תוצאות המודל תהיינה שונות).
- API דוחה קלט שאינו תקין, לרבות נושא ארוך מ-100 תווים, גם אם נשלח ישירות ולא דרך הממשק.
- ה-API מחזיר את מבני התשובה והקודים המוגדרים בארכיטקטורה, ללא Cache של בדיחות.
- זמן תגובה טיפוסי (מדידה של 5 בקשות לפחות) של כ-5 שניות; אם ארוך משמעותית — מדווחים לבעל המוצר.
- המפתח אינו מופיע ב-Bundle של ה-Frontend, בבקשות שיוצאות מהדפדפן או בתגובות ה-API.
- נבדקה גישה ממשית ל-`gpt-5`; אם אינו זמין לחשבון, עוצרים ומציגים לבעל המוצר את החסימה — לא מחליפים מודל על דעת עצמנו.

## Milestone 3 — חוויית שימוש שלמה והפעלת PWA 🟡

**שם ומטרה:** להפוך את זרימת יצירת הבדיחה לאמינה וברורה במצבי טעינה, כשל וניתוק, ולאפשר התקנה ופתיחה Offline.

**דרישות מוקדמות מבעל המוצר:**
- קובץ `spec/assets/app-icon.png` (ראה DESIGN 2.4.1).
- טלפון Android ו/או iPhone עם Chrome לבדיקת ההתקנה, לאחר הדחיפה.

**מה יש לממש:**
- כל מצבי המסך לפי טבלת המצבים ב-DESIGN 1.4: טעינה, בדיחה, שגיאה, נושא לא מתאים ו-Offline, עם הטקסטים מ-DESIGN 1.3.
- כלל ההבחנה בין Offline לשגיאה כפי שמוגדר ב-ARCHITECTURE 2.6, וביטול הבקשה בצד הלקוח אחרי 25 שניות.
- לאחר כשל ניתן לנסות שוב באופן יזום, ללא Retry אוטומטי שעלול להפיק חיוב כפול.
- הגדרת `vite-plugin-pwa` (`registerType: 'autoUpdate'`), Web App Manifest, אייקונים שנגזרים מ-`app-icon.png`, Service Worker ו-Caching של קובצי המעטפת בלבד — כולל גופנים ותמונת החתלתול. אין לשמור תשובות בדיחה במטמון או באחסון מתמשך.
- בדיקת גלילה לקריאת בדיחות ארוכות ושימור פריסת מובייל.

**תוצר מצופה:** האפליקציה מוכנה לשימוש ולהתקנה כ-PWA, עם חיווי ברור במצבים הרלוונטיים ויכולת לפתוח את הממשק בלי אינטרנט לאחר טעינה/התקנה מוצלחת.

**Definition of Done:**
- בזמן יצירה ההודעה הנכונה גלויה ולא ניתן להפעיל בקשה נוספת באמצעות הכפתור; בסיום הבקשה הכפתור חוזר להיות זמין.
- כשל API/רשת ו-Timeout מוצגים בעברית לפי DESIGN 1.3; ניתן להפעיל ניסיון חוזר ולקבל בדיחה כאשר השירות חוזר לעבוד.
- לאחר שהאפליקציה נטענה ברשת, ניתן לפתוח אותה ללא חיבור — עם הגופנים ותמונת החתלתול; ניסיון יצירה במצב זה מציג את הודעת ה-Offline ולא יוצר בדיחה.
- בכתובת הציבורית, בטלפון אמיתי: ב-Android מופיעה אפשרות התקנה ב-Chrome; ב-iPhone ההתקנה נבדקה בהתאם למגבלות iOS המתועדות בארכיטקטורה (או תועד שאינה זמינה).
- בדיחות ונתוני נושא אינם נשמרים כנתונים עסקיים בין הפעלות, ותגובות `/api/joke` אינן נשמרות במטמון.
- מראה המצבים נשאר באותו מסך, ללא מודאלים/תפריטים/דפים חדשים.

## Milestone 4 — הקשחת Production ובדיקות קבלה סופיות

**שם ומטרה:** לוודא שהאפליקציה הציבורית מאובטחת, מוגדרת נכון ועוברת את כל בדיקות הקבלה.

**דרישות מוקדמות מבעל המוצר:**
- אם רוצים מפתח OpenAI נפרד ל-Production — יצירתו והזנתו ב-Vercel (בהדרכה).

**מה יש לממש:**
- וידוא הפרדת `OPENAI_API_KEY` בין הסביבות ב-Vercel ככל שהוגדר בארכיטקטורה; אין לכלול מפתחות בקוד או ב-Git.
- כותרות אבטחה (`X-Content-Type-Options`, `Referrer-Policy`, CSP שאינה חוסמת את ה-Service Worker) ו-`Cache-Control: no-store` ל-`/api/joke`.
- בדיקות קבלה בכתובת הציבורית ב-Chrome על Android ועל iPhone, כולל RTL, יצירת בדיחה, נושא לא מתאים, שגיאות, התקנת PWA והתנהגות Offline בהתאם לאפשרויות מערכת ההפעלה.
- וידוא שתקרת ההוצאה והתראות התקציב ב-OpenAI פעילות; אין להוסיף Rate Limiting בניגוד ל-PRD.

**תוצר מצופה:** האפליקציה זמינה לציבור ב-Vercel, מאובטחת לפי הארכיטקטורה, ניתנת להתקנה במכשירים שבהם Chrome והמערכת תומכים בכך, וניתנת לעדכון באמצעות Push ל-GitHub.

**Definition of Done:**
- כתובת Production עם HTTPS מציגה את המסך היחיד וה-API פועל באותו Origin.
- בדיקות הקבלה של Milestones 1–3 עוברות בסביבת Production, לרבות שגיאות, נושא ריק, נושא לא מתאים, התאמת שפה והחלפת בדיחה קיימת.
- כותרות האבטחה ו-`no-store` מופיעות בתגובות.
- אין חשיפה של `OPENAI_API_KEY` ל-Frontend, ל-Repository או לתגובות API; הסוד קיים רק בהגדרות שרת מקומיות/Hosting כנדרש.
- דחיפה מאושרת ל-`main` מובילה אוטומטית ל-Production Deployment תקין ללא פעולה ידנית.
- נבדקו התקנה ופתיחה Offline במכשירים הנתמכים בפועל, ותועדו מגבלות אפשריות של Chrome ב-iPhone מבלי להבטיח זהות מלאה ל-Android.
- בעל המוצר אישר שתקרת ההוצאה והתראות התקציב ב-OpenAI מוגדרות ופעילות.

## Development Execution Rules — הוראות מחייבות ל-AI המבצע

1. **יש לפתח את ה-Milestones אך ורק לפי הסדר המתואר במסמך.** כל שלב נשען על התוצר שעבר בדיקות בשלב שקדם לו.
2. **בסיום כל Milestone יש לעצור את הפיתוח**, להציג למשתמש מה מומש, כיצד ניתן להפעיל ולהתנסות בתוצר, ואת תוצאות הבדיקות מול **כל** סעיפי ה-Definition of Done; יש לציין במפורש כשלים, מגבלות או בדיקות שלא ניתן היה לבצע.
3. **אין להתחיל את ה-Milestone הבא בלי אישור מפורש של המשתמש**, גם אם כל הבדיקות עברו.
4. אין להוסיף פיצ'רים, לשנות מודל AI, להוסיף Database או לשנות דרישות מוצר בניגוד ל-PRD ללא אישור מפורש.
5. בדיקות שדורשות טלפון אמיתי בכתובת הציבורית: לפי CLAUDE.md ("Milestone שדורש push כדי להשלים אותו"), עוצרים ומבקשים אישור ל-push **לפני** סימון ✅. אחרי ה-push בעל המוצר בודק בטלפון, ורק אז ה-Milestone מאושר. עד אז סעיפים אלה מסומנים ב-DoD כ"ממתינים לבדיקה בטלפון" ולא כעוברים.
